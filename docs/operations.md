# Эксплуатация

## Запуск и CLI

```bash
sudo vpn-orchestrator -c /etc/vpn-orchestrator/config.toml
```

| Параметр | Назначение |
| --- | --- |
| `-c`, `--config <PATH>` | Путь к TOML, по умолчанию `/etc/vpn-orchestrator/config.toml`. |
| `--monitor-interval <SECS>` | Интервал логирования пиров серверного интерфейса, по умолчанию 30 секунд. |
| `--skip-server` | Не вызывает `wg-quick`/`awg-quick` для серверного интерфейса. |
| `--log-file <PATH>` | Переопределяет `[logging].file`. |
| `--quiet` | Отключает логирование. |

## Failover и direct fallback

1. Сервис поднимает все включённые upstream-интерфейсы и подготавливает отдельные маршруты для проб.
2. Первый upstream, прошедший health-check и успешную настройку маршрута/NAT, становится активным. При ошибке активации после отката сервис пробует следующий; если кандидатов нет, переходит в fallback.
3. После `failover_threshold` неудач активного upstream сервис ищет доступный upstream в порядке конфигурации.
4. При переключении обновляются клиентский маршрут и, если включён `masquerade`, NAT/FORWARD-правила. Если настройка NAT неудачна, сервис пытается восстановить прежний маршрут и правила.
5. Если здоровых VPN нет, сервис остаётся запущенным, проверяет готовые upstream каждые 10 секунд и настраивает прямой выход через обычный default route из `main`. Неудачные фоновые восстановления повторяются с backoff, описанным ниже.
6. После восстановления VPN клиентский маршрут и NAT возвращаются на него.

Прямой fallback означает, что маршрутизация настроена без VPN. Он не доказывает доступность внешнего интернета. Если у сервера нет подходящего IPv4 default route или его нельзя применить, клиентская таблица очищается, а событие `direct_fallback_failed` сообщает о недоступности клиентского выхода.

При остановке сервис удаляет свои маршруты и NAT/FORWARD-правила. Существующий настроенный WG/AWG-интерфейс в состоянии DOWN поднимается через `ip link set ... up`, без повторного создания через quick. При остановке сервис опускает только интерфейсы, которые создал сам; внешне управляемые интерфейсы остаются поднятыми.

## Логи

По умолчанию логи идут в stdout на уровне `info`. `RUST_LOG` имеет приоритет над `[logging].level`.

```toml
[logging]
enabled = true
file = "/var/log/vpn-orchestrator.log"
level = "info"
max_size_mb = 10
keep_mb = 1
```

`max_size_mb = 0` отключает лимит. При положительном лимите `keep_mb` должен быть меньше него; `keep_mb = 0` очищает файл при ротации. Один файловый writer сохраняет последние полные строки, поэтому нет гонки между rename и записью. Медленный диск может задерживать логирование. Ошибки файла выводятся в stderr как `log_write_failed`, восстановление — `log_write_restored`. Сохранение очереди не гарантируется при `SIGKILL`, аварии диска или питания.

Ключевые события:

- `vpn_unavailable` — не осталось доступного VPN;
- `direct_fallback_enabled` — клиентский маршрут переключён на обычный интерфейс;
- `direct_fallback_failed` — не удалось настроить даже прямой выход;
- `vpn_still_unavailable` — отказ продолжается, запись не чаще раза в минуту;
- `vpn_restored` — VPN восстановлен и прямой выход отключён;
- `upstream_recovery_failed` — отказ фонового восстановления: `error` содержит причину (для раннего завершения Xray — exit status), `failures` — число последовательных неудачных попыток, `retry_ms` — задержку, `next_retry_unix_ms` — ближайшее допустимое время новой попытки в миллисекундах Unix UTC;
- `upstream_recovery_succeeded` — восстановление после отказов подтверждено health-check, `attempts` включает успешную попытку; backoff сброшен;
- `https_probe_failed` и `https_probe_restored` — изменение HTTPS-доступности. При `RUST_LOG=debug` запись для каждого недоступного URL содержит причину curl.

## Диагностика

```bash
sudo journalctl -u vpn-orchestrator -f
ip route show table 100
ip rule list
sudo nft list table ip vpn_orchestrator_nat
sudo wg show
ip link show wg0 wg1
```

Дочерний `xray run` наследует stdout/stderr сервиса: при запуске через systemd его сообщения доступны в journal (если вывод unit не перенаправлен), в контейнере — в его stdout/stderr. Настройка `[logging].file` перенаправляет только записи оркестратора через `tracing`; отдельный вывод Xray в этот файл не копируется. Захват stderr Xray и дополнительный pipe не используются. Содержимое конфига Xray не добавляется в события восстановления; собственный вывод Xray зависит от его настроек журналирования.

Внешние firewall-цепочки могут блокировать FORWARD независимо от правил сервиса. При смене исходного VPN-адреса существующим TCP/UDP-сессиям может потребоваться переподключение.

## Восстановление и завершение команд

Восстановление каждого upstream и его таблицы проб выполняется в отдельной фоновой задаче. Медленный резерв не задерживает проверку активного VPN и переключение на уже готовый резерв. Для одного upstream одновременно работает не больше одной задачи восстановления. Без расширенного мониторинга восстановление проверяется каждые 10 секунд; включённый мониторинг также запускает его перед циклом проб.

После ошибки для каждого upstream отдельно сохраняются счётчик последовательных отказов и монотонный срок следующей попытки. Верхняя граница задержки растёт как 10, 20, 40, 80, 160, 300 секунд и далее остаётся 300 секунд. Equal jitter выбирает задержку от половины до полной границы: 5–10, 10–20, 20–40, 40–80, 80–160, затем 150–300 секунд. Задержка отсчитывается после обработки результата неудачной задачи; новая задача запускается не раньше срока, при следующем проходе основного цикла (обычно раз в секунду). Периодический опрос, ICMP-мониторинг, failover и speed test используют одно ограничение и не обходят его. Пропущенный запрос не увеличивает счётчик и не создаёт предупреждение о новом отказе.

После отказа сброс происходит только при успешных запуске upstream, подготовке маршрута проб и health-check. Если процесс уже работает, он переиспользуется. Ожидание срока не занимает recovery task и не задерживает active health-check или другие upstream. Без предшествующих отказов сохраняется обычная проверка запуска/маршрута без дополнительного health-check в recovery task. Состояние backoff хранится в памяти и начинается заново после перезапуска демона; формат конфигурации не меняется.

Команды управления сетью ограничены таймаутом 30 секунд. При отмене или таймауте на Linux/macOS завершается вся группа процессов команды, включая дочерние команды `wg-quick`/`awg-quick`. При остановке сервис отменяет и дожидается задач восстановления, затем очищает маршруты/NAT и созданные им интерфейсы, включая частично поднятые. На начальном запуске сервис дожидается ограниченных таймаутом команд инициализации, после чего обрабатывает сигнал остановки.

Отсутствующие правила при очистке допустимы. Остальные ошибки удаления собираются и сообщаются вместе; очистка следующих ресурсов продолжается. При неуспешной очистке процесс завершается с ненулевым кодом, поэтому systemd с `Restart=on-failure` может запустить его повторно. Полное время остановки зависит от числа ресурсов: таймаут действует на отдельную команду.
